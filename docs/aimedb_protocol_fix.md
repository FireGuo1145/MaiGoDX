# AimeDB 协议报文格式修复报告

针对杂鱼大哥哥反馈的“注册了 Keychip 但自检依然 Bad”的问题，我们重新审视了 AimeDB 的底层报文封装逻辑。发现问题的根源并不在 Keychip 校验逻辑，而是在 **AES 加密报文的对齐与长度描述** 上。

## 1. 核心问题定位

在 AimeDB 协议中，机台对报文头的要求极其严苛：
1. **报文长度描述不匹配**：本地代码在处理加密报文时，未能正确处理“协议逻辑长度”与“AES 块对齐长度”之间的差异。如果机台收到的报文头中 `length` 字段与实际加密块大小不一致，或者解密后的魔数校验位置偏移，就会直接判定 Aime 模块异常。
2. **响应头填充时机错误**：原先的代码在计算加密前没有对响应体进行强制 16 字节对齐填充，导致生成的加密包在某些特定指令（如自检握手）下长度非法。

---

## 2. 修复方案

我们在 `internal/handler/aimedb.go` 中实施了以下底层修复，以完全对齐 `AquaDX` 的行为：

### 2.1 修正报文读取与解密流
- **长度对齐处理**：在 `readAimeDBRequest` 中，现在会根据报文头描述的长度自动计算 AES 块对齐后的 `readLength`，确保完整读取加密帧，但在解密后会自动截断回协议所需的原始长度。
- **解密容错**：优化了 `cryptAimeDB` 函数，使其能够处理非 16 字节倍数的缓冲区（仅对完整块进行解密），防止因尾部字节导致的解密崩溃。

### 2.2 规范化响应包封装
- **强制对齐填充**：在 `writeAimeDBResponse` 中，我们在写入魔数（`0xa13e`）和版本号（`0x3087`）之前，会先将整个响应体填充至 16 字节的倍数。
- **头字段同步更新**：确保响应头中的长度字段（偏移 `0x06`）记录的是**对齐后**的实际发送长度，这是机台通过自检的关键。
